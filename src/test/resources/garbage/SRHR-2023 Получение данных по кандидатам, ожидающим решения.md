# SRHR-2023 Получение данных по кандидатам, ожидающим решения

## Написать миграции в srhr-ms-requisition для хранения данных по кандидатам ожидающим решения

1. Создать таблицу для кандидатов, ожидающих решения `pending_candidates` и соответствующую сущность

```json
id PK INTEGER
vacancy_id FK INTEGER (ссылка на идентификатор vacancy)
candidate_id VARCHAR
full_name VARCHAR  
approver_pernr VARCHAR
```

2. Создать таблицу для этапов кандидатов `pending_candidates_events` и соответствующую сущность

```json
id PK INTEGER
pending_candidate_id FK INTEGER  (ссылка на идентификатор pending_canidates)
event_code VARCHAR
status_date TIMESTAMP  
days integer  
expiration_zone integer
```

Запрос отправлять через Кафку в топик "srhr.requisition.to.easup", далее получать ответ от микросервиса srhr-ms-requisition в топике Кафки "srhr.requisition.from.easup" в формате, описанном выше и передавать на фронт. Использовать очередь Redis.

## Обработка запроса в микросервисе **srhr-ms-requisition**

При получении запроса от rest микросервиса необходимо:

1. Сделать запрос в Е-стафф с помощью srhr-master-data-integration POST /pending-candidates с табельным номером текущего пользователя в теле запроса.
2. Удалить записи из таблицы `pending_candidates` (с дочерней сущностью `pending_candidates_events`) по полю `approver_pernr` по значению табельного номера текущего пользователя. Сохранить полученные данные из Е-стафф.
3. Далее реализовать получение кандидатов, ожидающих решения из `pending_candidates` учитывая фильтр по **eventCode (условие ИЛИ)** (то есть выборка кадидатов, у которых есть хотя бы один этап из массива eventCode), свободный поиск по фио (полное вхождение, как в кандидатах на вакансию) и пагинацию.  
  <br/>**Дополнение.** Свободный поиск должен быть реализован не только по фио кандидата, полный список параметров по которым должен быть реализован свободный поиск:  
  \- по номеру заявки на подбор; `requisitions.number`  
  \- по ФИО кандидата; `pending_candidates.full_name`  
  \- по типу должности, т.е. по виду заявки на подбор; `requisitions.position_type`  
  \- по идентификатору штатной должности из вакансии; `requisitions.staff_position_id`  
  \- по наименованию штатной должности из вакансии; `requisitions.staff_position_name`  
  \- по идентификатору подразделения из вакансии. `requisitions.struct_unit_id`  
  \- по наименованию подразделения из вакансии. `requisitions.struct_unit_name`

  
Обсудили на встрече, что для реализации такого поиска необходимо обогатить таблицу `pending_candidates` всеми необходимыми атрибутами и сформировать в таблице новый генерируемы столбец `search_text`  
Связь между таблицами: `pending_candidates.vacancy_id -> vacancy.vacancy_id -> vacancy.requisition_guid -> requisitions.guid`  

4. Заполнить поле `count` - сколько ВСЕГО кандидатов, ожидающих решения текущего пользователя с учетом фильтров.
5. Отсортировать для каждого кандидата массив events по полю `status_date` от раннего к позднему.
6. Массив `eventCode` **заполнить ВСЕМИ уникальными кодами этапов** по всем кандидатам (на всех страницах), ожидающим решения текущего пользователя (руководителя), учитывая фильтры.
7. Обогатить ответ данными заявки на подбор (в ответе получили vacancyId → таблица vacancy → по requisition_guid → таблица requisitions и связь structure_unit).
