# Release Management

## Цель

Описать единые правила подготовки, выпуска и сопровождения релизов.

---

## Общие договоренности
Вначале каждого нового планирования, на новый релиз, определяется ответственный за релиз или группа разработчиков, 
которые будут отвечать за подготовку релиза. 
Для каждого релиза создаётся отдельная страница release notes. 
На этой странице, каждый разработчик добавляя новую фичу в `release/*`, должен добавить инфо об этой фиче и затрунутом сервисом. 
Если есть критичная инфа о поставке, тоже её указать.

## Version strategy

Для версионирования используем формат:

`MAJOR.MINOR.PATCH`

Где:
- `MAJOR` — номер суперспринта;
- `MINOR` — номер релиза внутри суперспринта;
- `PATCH` — номер hotfix / срочного исправления внутри релиза.

Примеры:
- `1.0.0` — первый релиз первого суперспринта;
- `1.1.0` — второй релиз первого суперспринта;
- `1.1.1` — первый hotfix для релиза `1.1.0`;
- `2.0.0` — первый релиз второго суперспринта.

---

## Release branches

Release-ветка создаётся от создаётся от `release/*` текущей версии, в момент когда объявленно о стабилизации текущего релиза.
`release/*` является и веткой для сбора новых фичей, и затем веткой стабилизации релиза.

Формат ветки:
`release/MAJOR.MINOR.PATCH`

Пример:
`release/1.1.0`

---

## Перед выпуском релиза необходимо:

- убедиться, что все необходимые задачи влиты в `release`;
- обновить версию приложения;
- собрать приложение;
- пройти минимальные проверки;
- исправить найденные дефекты в `release/*`;
- убедиться, что релизная ветка готова к merge в `master`.

---

## Когда релиз готов:

1. `release/*` мержится в `master` с tag(`v1.1.0`) с номером версии;
2. выполняется deploy в production;

---

## Bugfix process

Используется для исправления ошибок при стабилизации релиза

Bugfix создается от `release/*`

Формат ветки: `bugfix/SRHR-XXXX`

Bugfix мержится обратно в `release/*`

---

## Hotfix process

Hotfix используется только для срочных исправлений production.

Hotfix-ветка создаётся от `master`.

Формат ветки:
`hotfix/MAJOR.MINOR.PATCH`

Пример:
`hotfix/1.1.1`

После завершения hotfix:

1. `hotfix/*` мержится в `master` создаётся новый tag;
2. выполняется deploy в production;
3. при необходимости изменения также возвращаются в активную `release/*`.

---

## Release documentation

Для каждого релиза создаётся отдельная страница:

`releases/MAJOR.MINOR.PATCH.md`

Каждый разработчик когда добавляет новую фичу, должен добавить инфо об этой фиче и затрунутом сервисом. 
Если есть критичная инфа о поставке, тоже её указать.


---

## Release checklist

Перед выпуском проверить:

- [ ] версия приложения обновлена;
- [ ] MR в `master` создан из правильной `release/*` ветки;
- [ ] build зелёный;
- [ ] критичные проверки пройдены;
- [ ] release notes обновлены;
- [ ] команда уведомлена о выпуске.

---

## Rollback

Если после релиза обнаружена критичная проблема, команда принимает одно из решений:

- откатить deploy на предыдущую стабильную версию;
- выпустить срочный hotfix;

Решение принимает ответственный за релиз совместно с командой.
