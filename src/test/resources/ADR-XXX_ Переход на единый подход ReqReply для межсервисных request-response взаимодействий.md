# ADR-XXX: Переход на единый подход ReqReply для межсервисных request/response взаимодействий

## Статус

Proposed

## Контекст

В ряде сервисов используется асинхронное взаимодействие между сервисами поверх Redis и Kafka, которое с точки зрения вызывающего сервиса представляет собой синхронный request/response вызов.

Текущая схема выглядит следующим образом:

```text
REST request
    ↓
Redis Queue
    ↓
Scheduler
    ↓
Kafka Request
    ↓
Worker Service
    ↓
Business Logic
    ↓
Kafka Response
    ↓
Redis by correlationId
    ↓
Polling Redis
    ↓
REST response
```

Подобная схема реализована отдельно в нескольких сервисах и включает повторяющуюся инфраструктурную логику:

- формирование сообщения;
- передачу системных параметров;
- генерацию и использование `correlationId`;
- сериализацию и десериализацию request/response;
- постановку сообщения в Redis;
- перенос сообщения из Redis в Kafka;
- ожидание ответа;
- обработку timeout;
- получение ответа из Kafka;
- сохранение ответа по `correlationId`;
- поддержку сообщений, превышающих допустимый размер Kafka;
- восстановление сообщений из filestorage;
- маршрутизацию входящего запроса на конкретную бизнес-операцию.

При этом конкретные сервисы реализуют эту механику самостоятельно.

Это приводит к следующим проблемам:

- дублирование инфраструктурного кода;
- различия в реализации одного и того же request/response сценария между сервисами;
- смешивание транспортной и бизнес-логики;
- сложность сопровождения и изменения протокола взаимодействия;
- необходимость отдельно реализовывать timeout, correlation и обработку ошибок;
- сильная зависимость бизнесовых DTO от транспортных параметров;
- сложность добавления новых типов взаимодействий;
- polling Redis создает лишнюю нагрузку и блокирующее ожидание;
- изменение транспортного механизма требует изменений в каждом сервисе.

## Решение

Ввести единый подход **ReqReply** для межсервисных взаимодействий, которым требуется логическая модель:

```text
Request → Processing → Response
```

независимо от того, что физически взаимодействие выполняется через Redis, Kafka и другие инфраструктурные компоненты.

ReqReply становится общим инфраструктурным механизмом, скрывающим детали транспорта от бизнесового кода.

Целевая схема:

```text
Caller
   ↓
ReqReply
   ↓
RequestEnvelope<T>
   ↓
Transport
   ↓
ReqReply Consumer
   ↓
RequestHandler<T, R>
   ↓
UseCase
   ↓
ResponseEnvelope<R>
   ↓
Transport
   ↓
ReqReply
   ↓
Caller
```

## Унифицированный контракт

Для запросов вводится общий транспортный контракт:

```java
RequestEnvelope<T>
```

Он содержит:

- `correlationId`;
- `requestType`;
- системные параметры взаимодействия;
- `payload`.

Бизнесовые параметры конкретной операции помещаются только в:

```java
T payload
```

Например:

```java
RequestEnvelope<PendingCandidatesRequest>
```

Для операций без бизнесового тела допускается:

```java
RequestEnvelope<Void>
```

Для ответа используется:

```java
ResponseEnvelope<R>
```

который содержит:

- `correlationId`;
- `requestType`;
- результат операции;
- информацию об ошибке при неуспешном выполнении.

Таким образом системные параметры больше не должны дублироваться в каждом бизнесовом DTO.

## ReqReply Producer

Вызывающий сервис взаимодействует с ReqReply через единый API.

Концептуально:

```java
ResponseEnvelope<R> getResponse(
        RequestEnvelope<T> request,
        Class<R> responseType
);
```

Внутренняя реализация ReqReply отвечает за:

- сериализацию запроса;
- проверку размера сообщения;
- сохранение большого сообщения в filestorage;
- отправку сообщения;
- регистрацию ожидания по `correlationId`;
- получение ответа;
- timeout;
- десериализацию ответа.

Вызывающий код не должен знать, каким образом request был доставлен и каким образом был получен response.

## ReqReply Consumer

На принимающей стороне ReqReply выполняет общую подготовку запроса до входа в бизнесовую логику.

Обработка строится по схеме:

```text
Incoming Message
      ↓
Deserialize
      ↓
Prepare Request
      ↓
Resolve Handler
      ↓
Deserialize Payload
      ↓
UseCase
      ↓
Prepare Response
```

Общая техническая обработка выполняется один раз для всех типов запросов.

Конкретная бизнесовая операция подключается через:

```java
RequestHandler<T, R>
```

Например:

```text
requisition_pending_candidates
        ↓
PendingCandidatesHandler
        ↓
PendingCandidatesUseCase
```

Таким образом ReqReply отвечает за инфраструктурную часть, а UseCase — только за бизнес-операцию.

## Correlation и ожидание ответа

`correlationId` является обязательной частью ReqReply-контракта и используется для связывания request и response.

Текущая реализация ожидания ответа через периодический Redis polling должна рассматриваться как временная реализация ReqReply.

Целевой вариант — событийное завершение ожидания:

```text
Request
   ↓
CompletableFuture registered by correlationId
   ↓
Response
   ↓
correlationId
   ↓
complete future
```

Для нескольких экземпляров приложения локальный `CompletableFuture` дополняется распределенной сигнализацией, например Redis Pub/Sub:

```text
Kafka response
      ↓
Redis response storage
      ↓
Redis Pub/Sub
      ↓
Pod with pending correlationId
      ↓
future.complete(...)
```

Таким образом транспорт ожидания может изменяться без изменения API ReqReply и вызывающего бизнесового кода.

## Поддержка больших сообщений

Существующий механизм вынесения больших сообщений в filestorage сохраняется как часть ReqReply.

Если размер сообщения не превышает ограничение транспорта:

```text
RequestEnvelope
      ↓
Kafka
```

Если превышает:

```text
RequestEnvelope
      ↓
Filestorage
      ↓
compact message + fileUuid
      ↓
Kafka
```

На принимающей стороне ReqReply автоматически восстанавливает исходное сообщение до передачи его в Handler/UseCase.

Аналогичный механизм применяется к большим ответам.

Бизнесовый код не должен учитывать наличие `fileUuid`.

## Граница ответственности

### ReqReply отвечает за

- request/response envelope;
- `correlationId`;
- serialization/deserialization;
- отправку и получение сообщений;
- ожидание ответа;
- timeout;
- восстановление больших сообщений;
- обработку filestorage;
- общую подготовку системного контекста;
- маршрутизацию на Handler;
- общую обработку ответа;
- унифицированную обработку технических ошибок.

### Handler отвечает за

- соответствие `requestType` конкретной операции;
- тип входного payload;
- вызов соответствующего UseCase.

### UseCase отвечает за

- бизнес-логику конкретной операции.

UseCase не должен зависеть от:

- Kafka;
- Redis;
- polling;
- filestorage;
- JSON;
- `correlationId`;
- механизма доставки request/response.

## Архитектурное размещение

Универсальная часть ReqReply должна быть отделена от конкретных бизнес-сервисов и рассматриваться как кандидат на общую библиотеку.

Концептуально:

```text
request-reply
├── model
│   ├── RequestEnvelope
│   ├── ResponseEnvelope
│   └── PreparedRequest
├── handler
│   ├── RequestHandler
│   ├── RequestHandlerResolver
│   └── RequestHandlerExecutor
├── producer
├── consumer
└── exception
```

Конкретные сервисы предоставляют:

```text
business-service
├── handlers
├── usecases
├── request DTO
└── response DTO
```

Интеграции с Kafka, Redis, filestorage и другими внешними системами реализуются инфраструктурным слоем.

## Последствия

### Положительные

- единый способ реализации request/response взаимодействий между сервисами;
- сокращение дублирования инфраструктурного кода;
- отделение бизнес-логики от Redis/Kafka;
- единый механизм correlation и timeout;
- единая поддержка больших сообщений;
- типизированные business request/response;
- возможность централизованно изменить механизм ожидания ответа;
- возможность убрать Redis polling без изменения бизнесового API;
- упрощение добавления новых взаимодействий;
- возможность повторного использования ReqReply в нескольких сервисах;
- упрощение тестирования UseCase.

### Отрицательные

- появляется дополнительный инфраструктурный слой;
- потребуется миграция существующих взаимодействий;
- на переходном этапе старый и новый механизмы будут существовать параллельно;
- универсальная библиотека потребует стабильного контракта и обратной совместимости;
- ошибки в общей ReqReply-реализации потенциально затрагивают несколько сервисов.

## Рассмотренные альтернативы

### Сохранить отдельную реализацию request/response в каждом сервисе

Отклонено из-за дублирования кода и различий в поведении одинаковых сценариев.

### Перейти полностью на синхронные HTTP-вызовы

Не принимается как универсальная замена.

Для существующих взаимодействий Kafka используется как часть интеграционного и эксплуатационного контракта, поэтому ReqReply должен абстрагировать транспорт, а не заменять его HTTP.

### Оставить Redis polling как целевое решение

Не принимается как целевая архитектура.

Polling может временно использоваться как реализация ожидания внутри ReqReply, но вызывающий код не должен зависеть от него.

## Стратегия миграции

Переход выполняется постепенно.

1. Ввести общий `RequestEnvelope<T>` и `ResponseEnvelope<R>`.
2. Ввести ReqReply API для отправки запроса и ожидания ответа.
3. Перевести одно взаимодействие на новый контракт.
4. Вынести общую обработку принимающей стороны в ReqReply Consumer.
5. Ввести `RequestHandler<T, R>` вместо централизованных `switch(requestType)`.
6. Перевести существующие бизнесовые DTO на отдельный `payload`.
7. Сохранить поддержку filestorage как внутреннюю часть ReqReply.
8. Перевести остальные взаимодействия на новый подход.
9. Заменить Redis polling на событийный механизм ожидания, не меняя публичный ReqReply API.
10. После стабилизации вынести универсальные компоненты в общую библиотеку.

## Итог

Принимается переход на единый подход **ReqReply** для межсервисных взаимодействий, которым требуется request/response семантика поверх асинхронного транспорта.

ReqReply инкапсулирует Kafka, Redis, correlation, timeout, сериализацию и работу с большими сообщениями.

Бизнесовые сервисы работают с типизированными `RequestEnvelope<T>` / `ResponseEnvelope<R>`, а конкретные UseCase остаются независимыми от механизма доставки сообщений.
