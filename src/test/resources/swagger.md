# Работа с Swagger / OpenAPI

## Назначение

Для сервисов, предоставляющих публичное API, например сервисов с суффиксом `*-rest`, необходимо публиковать актуальное описание API в формате OpenAPI.

OpenAPI-спецификация должна формироваться непосредственно из работающего приложения. Это позволяет гарантировать, что опубликованный Swagger соответствует фактически реализованным контроллерам, моделям запросов и ответов.

## Генерация OpenAPI-спецификации

Swagger необходимо генерировать при помощи интеграционного теста.

Пример теста:

```java
public class OpenApiDocumentationIntegrationTest extends BaseIntegrationTest {

    @Test
    void shouldGenerateOpenApiYaml() throws Exception {
        byte[] openApiYaml = mockMvc.perform(get("/v3/api-docs.yaml"))
                .andExpect(status().isOk())
                .andReturn()
                .getResponse()
                .getContentAsByteArray();

        Path outputFile = Path.of(
                "build",
                "generated",
                "openapi",
                "openapi.yaml"
        );

        Files.createDirectories(outputFile.getParent());
        Files.write(outputFile, openApiYaml);
    }
}
```

Интеграционный тест:

1. Запускает Spring-контекст приложения.
2. Выполняет запрос к endpoint:

```text
/v3/api-docs.yaml
```

3. Проверяет успешность ответа.
4. Сохраняет полученную OpenAPI-спецификацию в файл:

```text
build/generated/openapi/openapi.yaml
```

## Запуск генерации

Для генерации Swagger необходимо запустить интеграционный тест:

```bash
./gradlew test --tests "*OpenApiDocumentationIntegrationTest"
```

После успешного выполнения теста файл будет находиться по пути:

```text
build/generated/openapi/openapi.yaml
```

Каталог `build` является генерируемым и не должен использоваться как постоянное место хранения опубликованной спецификации.

## Нормализация файла

Перед публикацией необходимо нормализовать форматирование сгенерированного YAML-файла.

Под нормализацией понимается:

* использование единообразных переносов строк;
* использование окончания строк `LF`;
* удаление лишних пустых строк;
* наличие одного переноса строки в конце файла;
* единообразное форматирование YAML;
* отсутствие изменений, не влияющих на содержимое контракта.

Вместо формулировки «выровнять файл по переносам» рекомендуется использовать:

> Нормализовать форматирование и окончания строк OpenAPI-файла.

Для форматирования можно использовать Swagger Editor, встроенное форматирование IDE или другой YAML-форматтер.

При форматировании запрещено вручную изменять состав endpoint, модели, обязательность полей и другие элементы API-контракта. Такие изменения должны вноситься в исходный код сервиса, после чего спецификация должна быть сгенерирована повторно.

## Публикация

После генерации и нормализации файл необходимо перенести в проект:

```text
service-swagger
```

Файл следует разместить в каталоге, соответствующем сервису и принятой в `service-swagger` структуре.

Публикуемый файл должен быть получен из актуальной версии сервиса и соответствовать изменениям, включаемым в Pull Request.

## Порядок обновления Swagger

При изменении публичного API необходимо:

1. Внести изменения в контроллеры, DTO и OpenAPI-аннотации сервиса.
2. Запустить интеграционные тесты сервиса.
3. Сгенерировать файл:

```text
build/generated/openapi/openapi.yaml
```

4. Нормализовать форматирование и окончания строк файла.
5. Проверить спецификацию через Swagger Editor.
6. Перенести актуальный файл в проект `service-swagger`.
7. Проверить изменения через `git diff`.
8. Убедиться, что в спецификации отсутствуют случайные или не относящиеся к задаче изменения.
9. Создать Pull Request с обновлением Swagger.

## Основные правила

* Swagger публикуется только для сервисов с публичным API.
* OpenAPI-файл генерируется из работающего приложения интеграционным тестом.
* Ручное написание или редактирование API-контракта не допускается.
* Изменения API сначала вносятся в код сервиса.
* После изменения публичного API Swagger должен быть сгенерирован повторно.
* Сгенерированный файл из каталога `build` не коммитится в репозиторий сервиса.
* В проект `service-swagger` переносится нормализованная версия файла.
* Изменение публичного API без обновления Swagger считается незавершённым.

## Чек-лист

Перед публикацией необходимо убедиться, что:

* интеграционный тест успешно выполнен;
* endpoint `/v3/api-docs.yaml` доступен;
* файл `build/generated/openapi/openapi.yaml` сформирован;
* форматирование и окончания строк нормализованы;
* спецификация успешно открывается в Swagger Editor;
* в Swagger присутствуют новые или изменённые endpoint;
* DTO запросов и ответов соответствуют реализации;
* отсутствуют случайные изменения контракта;
* актуальный файл перенесён в `service-swagger`.
