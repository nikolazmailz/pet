ШАБЛОН РАБОТЫ МОДЕЛИ (как отвечать)

Когда пользователь просит реализовать фичу, отвечай в такой структуре:
Короткий план изменений (списком, 5–10 пунктов).
Код по слоям (domain → application → controllers → infra → config).
Тесты (unit + integration, где уместно).
Конфигурация (application.yml, gradle зависимости — только если нужно).
Пояснения по важным решениям (коротко).
Требование: код должен компилироваться и быть согласованным (типы, импорты, названия пакетов).

ДОПОЛНИТЕЛЬНЫЙ БЛОК: КОНТРОЛЬ ОБЪЁМА КОДА (ОБЯЗАТЕЛЬНО)
6.1) Правило объёма генерации кода
Никогда не пиши весь код приложения целиком. Генерируй строго столько кода, сколько явно запрошено пользователем.

Если пользователь просит:
«покажи domain слой» → пиши только domain
«реализацию use-case» → пиши только application слой
«контроллер» → пиши только controller + нужные DTO
«тест» → пиши только тест, без реализации
Не добавляй код “на будущее”
Не дописывай соседние слои
Не догадывайся, что «логично было бы добавить ещё» - если об этом не просят

6.3) Явное ограничение объёма (строка для пользователя)
В каждом ответе ориентируйся на явное ограничение:
Писать код строго в пределах запроса пользователя.
Если пользователь указал:
«напиши только X»
«покажи пример»
«без тестов»
«без инфраструктуры»
→ это жёсткое ограничение, которое нельзя нарушать.

6.4) Формат ответа при частичной реализации
Если реализация неполная по архитектуре, в конце ответа добавляй краткий блок:
⚠️ Реализация намеренно ограничена:
- реализовано: X
- не реализовано: Y (по запросу пользователя)
